# 「品观」豆粕期货研究台 · 综合评估报告
> **评估对象**：品观 · 期货品种数据与研究台 (`mp-data`)  
> **评估维度**：技术工程架构 + 豆粕期货投资基本面与数据体系  
> **评估日期**：2026-11-23（已按代码实际实现核验修订）  

---

## 报告摘要

「品观」是一个定位清晰、工程克制且深度契合期货基本面投研逻辑的单品种（豆粕）研究工具。系统围绕**“外盘成本 vs 内盘供需”**这对核心矛盾，构建了最小必要数据集，通过轻量级工程方案实现了从数据抓取、派生计算、四维判断、静态渲染到安全门禁的全链路自动化。

* **工程架构**：推崇**零外部依赖（Zero External Dependencies）**与**静态预渲染（SSG）**，运维心智负担与资源开销极低；
* **投资基本面**：紧扣大宗商品产业逻辑（基差、相邻月差、豆菜粕价差、压榨利润、养殖利润、库存水平），没有沉溺于无效的指标堆砌；但库存“5 年分位”目前只是页面标签，实际计算为全历史排名分位。
* **非技术层面**：它本质是“一个人的晨报生产线”——真实降低了盘前信息获取成本，并在持续沉淀一份干净的私有产业数据；但其定位是**信息集中器而非判断引擎**，长期价值取决于录入纪律与“预期端”指标的补齐（详见第四部分）。

## 第一部分：技术与工程架构深度评价

### 1. 核心架构亮点与工程优势

#### 1.1 极致克制的无依赖设计（Zero External Dependencies）
* **纯标准库驱动**：核心服务完全基于 Python 3 标准库（`sqlite3`, `urllib`, `http.server`, `hmac`, `hashlib`, `secrets` 等），彻底摒弃了诸如 `requests`, `pandas`, `flask`, `fastapi` 等重型第三方库，做到零 `pip install`。
* **冷启动与环境抗老化**：避免了依赖地狱（Dependency Hell）与长周期运行后的依赖废弃，任何标准 Linux 环境（即便 1 核 1GB 内存 VPS）可在数秒内拉起运行。

#### 1.2 高内聚的 EAV 时序数据建模（Time-Series Data Modeling）
* **精炼的长表结构**：采用单表 `series (series_id, date, value, unit, freq, source, quality...)` 配以 `(series_id, date)` 复合主键，兼备时序扩展性与跨序列联查便利性。
* **编码即业务语义**：指标 ID 严格遵循投研层级命名规范（`A1.*` 行情、`A3.*` 外盘、`A4.*` 现货、`A5.*` 基差、`B1.*` 供给库存、`C1.*` 养殖需求），工程代码与业务手册形成 1:1 精确映射。

#### 1.3 健壮的防御性编程与自愈机制（Defensive Programming & Self-Healing）
* **脏数据过滤**：针对开盘前外部公共行情接口将结算价置 `0` 的天然缺陷，硬编码拦截零值，杜绝基差倒挂污染分析链。
* **日线回补自愈**：每次例行抓取自动拉取近期日线接口核对并补齐缺失的历史结算价，容错性强。
* **原始报文快照留档（Raw Snapshot）**：外部请求原始报文以二进制归档至 `raw/` 目录，便于反爬解析失效或数值分歧时快速定位追溯。
* **带抑止的健康体检（Health Check with Deduplication）**：`health.py` 对 5 个核心序列（现货、豆粕/大豆库存、开机率、养殖利润）做时效性校验，并检查基差阈值异动与近期非正结算价；12 小时内相同问题基于 SHA-1 指纹去重，杜绝告警风暴。

#### 1.4 实用的轻量安全与权限隔离（Pragmatic Security Architecture）
* **网络收敛**：Python API 仅监听 `127.0.0.1` 本地回环地址，不直面公网，由 Nginx 承接反向代理、静态托管与 TLS 终结。
* **作用域 Cookie 签名**：基于 HMAC-SHA256 实现了免 session 表的无状态鉴权，严格区分 `pinguan_auth`（只读，7天）与 `pinguan_admin`（管理/录入，24小时），跨权限无法越权冒充。
* **凭据去中心化管理**：密钥与配置移至 `/etc/mp-data/` 设权限 600，口令仅存 SHA-256 摘要（实现为固定前缀 `pinguan:` 后再哈希，属静态 pepper，并非随机盐），支持一键 Secret Rotation。

#### 1.5 高性能静态生成与成本受控的 LLM 集成（SSG & Frugal AI）
* **纯静态输出（SSG）**：Nginx 直接以纯静态方式对外提供服务，无客户端水合延迟，页面加载瞬时完成。
* **数据指纹缓存（Data Fingerprinting）**：盘前 AI 判断（`judge.py`）以事实数据的 MD5 指纹为缓存键，数据无实质变化不重复调用模型，节约 Token 成本；简报导语（`brief.py`）每日仅生成一次，未做指纹缓存。

### 2. 技术局限与潜在风险

1. **外部数据源单点依赖（Single Point of Failure, SPOF）**：
   * 期货行情、外盘与汇率全部依赖新浪免费接口。虽然大商所官网因 WAF（反爬机制，HTTP 412）无法直连，但新浪接口若遭遇频控或格式变更，缺少腾讯、网易、东财等备用降级数据源。现货侧另有生意社（100ppi）作对照口径，资讯侧依赖金十 MCP，这两条链路同样没有备份。
2. **核心供需数据依赖非官方抓取（Unofficial Scraping）**：
   * `mysteel.py` 以正则解析 Mysteel 文章，先落 `probe` 表，再由 `sync()` 按 `mysteel_sync` 映射写入正式序列（`quality=auto`），并已由 `mp-data-mysteel.timer` 每日 18:30 调度。HTML 结构一变即失效，还要面对 451 频率防护；这与 README 宣称的“核心付费数据手工录入”存在口径冲突。
3. **分位口径名不副实（Percentile Label Mismatch）**：
   * `render.py` 的 `percentile()` 用全部历史样本排名，未按“5 年同期”对齐，但样本一旦满 8 条，页面就固定标注“5年分位”。样本仅 8 周时会把“8 周分位”显示成“5 年分位”，容易误导判断。
4. **`render.py` 视图层耦合过重（Maintainability Risk）**：
   * `render.py` 约 1150 行，大量使用 Python 字符串拼装 HTML/SVG。虽省去 Jinja2 依赖，但在未来图表交互增强或响应式重构时，维护难度与修改心智负担较高。
5. **交易日历感知缺失（Trading Calendar Blindness）**：
   * 调度与时效性检测目前基于自然日偏移，缺少本地交易日历（Trading Day Calendar）对照。长假休市期间容易触发误报（如“已 N 天未更新”）。
6. **两处 TLS 校验被关闭（TLS Verification Disabled）**：
   * `mysteel.py` 与 `wasde.py` 均使用 `CERT_NONE`，在公共网络上抓取时无法防范中间人篡改，与“安全门禁”的整体定位不匹配。
7. **工作区目录含私钥文件（Credential Hygiene）**：
   * 根目录下存在 `.ssh/github_ed25519` 等私钥文件。尽管 `.gitignore` 已屏蔽，但将私钥存放在项目工作区根目录不属于标准实践，存在误打包或泄露风险。

## 第二部分：豆粕期货投资基本面与数据体系评价

### 1. 投研框架专业度分析

                  │ 豆粕期货定价核心矛盾框架      │

> 说明：美豆优良率、提货未执行、饲料库存天数、油粕比与“5 年同期分位”均属 `docs/数据源设计.md` 的规划项，当前尚未实现，下文不再将其计入既有能力。

#### 1.1 抓住了农产品“现实”与“预期”的核心逻辑
* **外盘是成本锚，内盘是供需阀**：该体系深谙“内盘豆粕涨跌不完全由国内自决”的基本规律，把 CBOT 美豆、美元兑人民币汇率、到港完税成本作为成本驱动；同时把国内油厂库存、开机率作为现货压力的温度计。
* **重视期限结构（Term Structure）**：不仅看单边价格，还自动追踪 **基差（Basis）**、**相邻活跃合约月差** 与 **豆菜粕价差（M - RM）**，并给出各自的历史分位。
  * *基差*：识别现货挺价还是宽松甩货，规避期货“深度贴水硬做空”或“大幅升水盲目追多”的现货收敛陷阱；
  * *月差*：按活跃合约相邻配对（如 `M2612-M2701`、`M2701-M2703`），识别近端供应矛盾（Back 结构）还是远期宽松预期（Contango 结构）；
  * *豆菜粕价差*：跟踪蛋白替代的相对强弱。系统只呈现价差与分位，**并未内置 400~800 元/吨的替代边界规则**，阈值判断仍需人工完成。

#### 1.2 引入历史分位数理念（Percentile Analysis）
* 理解农产品数据“孤立绝对值无意义”的特性：油厂周度豆粕库存同时展示环比变化、历史分位与绝对阈值，样本不足 8 条时降级为绝对水平判断，体现了对商品季节性规律的意识。
* **但实现与命名不符**：`percentile()` 统计的是全部历史样本排名，并未按“5 年同期”对齐，页面却固定标注“5年分位”。样本只有数周时，该标签会明显高估参考价值，属于应优先修复的偏差。

#### 1.3 务实但与文档不一致的数据获取（Pragmatic but Inconsistent Sourcing）
* 提供了 `manual.py`、网页录入与 `weekly` 周度汇总三种手工通道，并保留口径备注，方向正确。
* 但项目同时上线了 Mysteel 文章抓取：`mysteel.py` 正则解析后先落 `probe` 表，再由 `sync()` 按 `mysteel_sync` 映射写入正式序列（`quality=auto`），且已配置每日定时任务。这与 README“核心付费数据只做手工录入”的说法不一致，也使“手工数据可信度最高”的边界变得模糊。

### 2. 基本面体系的进阶优化空间

尽管框架极其扎实，但从资深期货研究与投资实战角度，仍有以下可以深化的维度：

#### 2.1 供给端：已有周度到港，缺前瞻船期
* **现状**：已设置 `B4.arrival`（周度大豆到港，手工录入，Mysteel 抓取也会同步），并与油厂大豆库存、周度压榨、开机率共同描述供给。
* **进阶建议**：真正缺的是“前瞻性”——巴西/美豆装船量与月度预估到港（通常每月 700~1000 万吨）。若能把船期排查与海关进口到港日历纳入，可对未来 1~2 个月的供给断档或洪峰提供预警。

#### 2.2 成本端：离岸升贴水（FOB Basis）的动态考量
* **现状**：到港成本公式完整（`(美豆 + 升贴水) × 0.367437 + 海运费`，再乘汇率、关税、增值税并加港杂费），但参数是静态配置：`premium_cents = 0`、`freight_usd = 35`、关税 13%、增值税 9%。
* **进阶建议**：南美丰产期或美西贴水波动剧烈时，升贴水对到港成本的影响可达 100~300 元/吨。应把南美/美湾大豆离岸升贴水与海运费改为可按周更新的输入变量，否则压榨利润更多反映“配置假设”而非市场现实。

#### 2.3 需求端：指标颗粒度偏粗
* **现状**：需求维度由“生猪自繁自养头均利润”（周度，手工）打分，另有生猪期货主力作为日频辅助观察，但未进入评分。
* **进阶建议**：
  * 生猪产能是慢变量，而饲料企业的**“物理库存天数”**和**“单周豆粕提货量”**是下游随用随采还是恐慌补库的最敏锐信号，这两项仍停留在 `数据源设计.md` 的规划阶段；
  * 白羽肉鸡/蛋鸡养殖利润同样对饲料蛋白需求有快速拉动作用，可作为辅助参考。

#### 2.4 四维研判规则的灵敏度调优
* **现状**：成本维度的打分依据是 CBOT 美豆单日涨跌幅是否超过 ±0.3%（`data["us"]["chg_pct"] > 0.3`）。
* **改进点**：在美豆隔夜波动中，0.3% 极其容易受短期噪音触发反复翻转。建议引入 **5日/20日均线趋势**，或结合 **USDA 月度供需报告（WASDE）超预期差** 给出更具趋势性的打分权重。

### 2. 后续迭代演化路线图 (Roadmap)

1. **短期（易实施，高收益）**：
   * **修正分位口径**：要么真正实现 5 年同期分位，要么把标签改为“历史分位”并标注样本区间，避免用 8 周数据冒充 5 年；
   * **恢复 TLS 校验**：移除 `mysteel.py`、`wasde.py` 中的 `CERT_NONE`；
   * **清理私钥存放**：将工作区 `.ssh/` 移入系统标准目录，消除误提交风险；
   * **引入法定交易日历（Trading Calendar）**：消除长假休市期间的健康告警误报；
   * **美豆涨跌平滑**：优化成本维度阈值规则，降低单日 0.3% 噪音翻转率。

2. **中期（架构解耦与多源保障）**：
   * **多行情源备灾（Fallback Data Sources）**：抽象行情适配层，新浪接口失效时无缝降级至腾讯或东方财富公开接口；
   * **抓取与手工数据仲裁**：明确 `quality=auto` 与 `manual` 的覆盖规则，同日期冲突时保留两者并标记，避免口径静默混用；
   * **视图层微模板化**：将 `render.py` 中的 HTML 骨架抽离为独立模板片段，提升可读性。

3. **长期（投研深度赋能）**：
   * **大豆船期与到港排期跟踪**：量化国内未来 4~8 周大豆月度到港节奏（周度到港已由 `B4.arrival` 覆盖）；
   * **下游补库情绪追踪**：增补饲料厂库存可用天数，完善需求维度的微观高频感知；
   * **补齐规划指标**：按 `数据源设计.md` 逐步接入美豆优良率、提货量与油粕比。

## 第四部分：非技术层面评价（只看项目结果与用途）

> 本部分抛开代码质量，只回答两个问题：**这个东西做出来是干什么的？用起来值不值？**

### 1. 本质定位：一个人的“晨报生产线”

卖方期货研究所每天的工作——收隔夜外盘、盯基差月差、查库存开机率、写晨报——本系统把它压缩为一个人、零边际成本的自动化流水线。对豆粕品种，交易者盘前需要扫的核心数字（CBOT、基差、相邻月差、豆菜粕价差、压榨利润、油厂库存、生猪利润）全部收拢在一页纸上，并自动推送邮件。**作为“降低信息获取成本”的工具，它是成功的**：这类信息原本散落在行情软件、资讯群与 Mysteel 文章里，每天至少消耗半小时拼凑，现在是一眼的事。

### 2. 价值构成：信息集中器，而非判断引擎

从结果导向看，最有价值的是前 80%，最薄弱的是后 20%：

* **真正值钱的部分——数据资产的滚动积累**：手工录入的库存、开机率、基差历史，配上来源与口径标签，持续运行两三年后即成为一份外部买不到、口径干净的个人产业数据库。这才是时间的复利：回测季节性、验证“库存分位到多少基差会走强”这类问题，靠的正是这套私有数据。
* **最薄弱的部分——判断层**：四维打分与 AI 简评的含金量偏低。以单日 ±0.3% 的美豆涨跌给成本端打分，本质上是把噪音翻译成信号，甚至有副作用——页面显示“成本：偏多”会制造一种已有结论的错觉。对成熟的交易者这层是装饰；对尚不成熟的交易者这层是误导。

因此它正确的用法是“**给我摆事实，判断我自己做**”。好在项目大部分按此逻辑构建（如豆菜粕价差只呈现分位、不内置替代边界），算得上克制。

### 3. 非技术层面的三大风险

1. **人的纪律是系统的单点**：库存、开机率、生猪利润依赖每周手工录入，录入一停，平台即退化为行情页面。健康告警只能提醒、不能代替干活。系统能否持续产生价值，取决于运营者能否坚持，而非代码本身。
2. **只看“现在”，不看“将来”**：没有船期、没有到港预估、没有下游库存天数——而豆粕期货定价的胜负手恰在预期差（下月到港洪峰还是断档、市场是否已 price in）。当前版本是一面照“现实”的镜子，对“预期”是盲的。作为回顾工具满分，作为前瞻工具欠半条腿。
3. **结果是自用的，没有第二用户**：访问码门禁、手工数据、私有部署，均表明其私人工具台定位。这不是缺点，但意味着评价它的唯一标准是“运营者的盘前效率与研究质量是否真实提升”，而非通用产品意义上的指标。

### 4. 一句话总评

这是一个**懂行的交易者给自己造的工具**，不是技术表演，也不是产品创业。它的用途定位——把碎片信息收拢为盘前一页纸、并长期沉淀一份干净的私有产业数据——是真实且被精准满足的；其内置的“判断”应视为草稿而非结论。长期价值上限取决于两件事：数据录入的坚持，以及能否补上“预期端”（船期、到港、下游库存）。补上那半条腿，它才能从“晨报工具”升级为真正的研究优势。
